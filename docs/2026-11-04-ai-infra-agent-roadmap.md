# AI Infra、Agent 与多模态 Pipeline 学习路线

## 主线与投入方式

建议先从推理与数据 Infra 切入，用一个“多模态文档检索与分析 Agent”串起模型服务、数据处理和 Agent 工作流。按每周 8–12 小时估算：约 60% 做实验，25% 读官方文档或源码，15% 整理可复现记录。

这是一份建议计划。下面的指标是验收口径，具体数值应由设备、模型、数据集和负载的实测结果确定。

## 分阶段安排

| 阶段 | 重点 | 应形成的产出 | 验收方式 |
| --- | --- | --- | --- |
| 第 1–2 周 | Linux、并发、内存与 I/O；PyTorch 推理和性能分析 | 环境记录、最小推理基线、一份性能分析报告 | 另一人可以按步骤复现；能区分数据准备、CPU 和设备计算耗时 |
| 第 3–5 周 | 推理服务、Prefill/Decode、KV Cache、批处理与排队 | 固定输入和负载的服务压测脚本、基线报告、一次受控优化 | 报告 TTFT、输出间隔、端到端延迟分位数、吞吐、峰值显存与失败率 |
| 第 6–8 周 | 图片与文档解析、Embedding、批推理、队列与数据质量 | 带数据版本和失败记录的多模态流水线 | 可追踪每个样本；支持失败重跑；能定位各处理阶段的吞吐瓶颈 |
| 第 9–12 周 | 工具调用、状态、Checkpoint、恢复与评测 | 接入前述服务和流水线的 Agent，以及固定任务集 | 检查任务成功率、引用正确性、工具错误率、时延和单任务资源消耗 |

## 第一阶段：把性能基线做扎实

先补会直接影响实验解释的基础：进程与线程、异步 I/O、缓存、内存分配、网络请求与数据库索引。历史课程资料按需查阅，不要求先读完整套课程。

使用 [PyTorch Profiler](https://docs.pytorch.org/tutorials/recipes/recipes/profiler_recipe.html) 观察算子耗时、形状和内存行为。记录 Python、PyTorch、设备、驱动及运行参数；没有合适 GPU 时，先完成预处理、接口和评测逻辑，设备相关结论留到相应环境验证。

## 第二阶段：先测服务，再做优化

先固定模型、输入长度、输出长度、请求到达方式、并发和采样参数，再比较批处理、缓存或调度配置。每次只改变少量变量，并保留原始测量结果。

[vLLM 的基准工具](https://docs.vllm.ai/en/stable/benchmarking/cli/) 提供服务压测与多模态处理阶段测量入口，可用来区分整体服务表现和输入处理开销。工具版本和具体参数应写进每次实验记录。

## 第三阶段：把多模态数据链路做可靠

先选择图片与文档作为输入，建立明确的数据 Schema、样本 ID、内容哈希、处理版本与错误记录。先跑通单进程链路，再根据瓶颈增加批处理、CPU/GPU 阶段拆分和并行执行。

[Ray Data 的 LLM 处理文档](https://docs.ray.io/en/latest/data/working-with-llms.html) 可作为多阶段批推理流水线的参考。引入框架后仍要分别测量读取、预处理、模型执行和结果写回的成本。

## 第四阶段：让 Agent 有明确的执行状态

先完成“检索文档—调用分析工具—汇总证据—输出答案”的有限步骤工作流，再增加分支与恢复。为工具定义输入输出契约、超时、可重试错误和幂等要求。

[LangGraph 的持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence) 区分线程内的 Checkpoint 和跨线程的数据存储，适合用来理解恢复执行与长期信息存储的边界。持久化方案还应经过进程重启和工具失败测试。

## 后续深入训练 Infra

端到端推理项目稳定后，再围绕一个可复现训练任务学习 [DDP](https://docs.pytorch.org/tutorials/intermediate/ddp_tutorial.html)、[FSDP2](https://docs.pytorch.org/tutorials/intermediate/FSDP_tutorial.html)、集合通信与并行策略。用计算、通信和显存的测量结果决定是否继续深入 CUDA、Triton 或分布式调度。

## 每篇实验笔记固定回答什么

1. 要解决的具体问题与可复现环境是什么？
2. 基线如何测量，输入和负载是否一致？
3. 修改了什么，瓶颈证据是什么？
4. 性能、质量、失败率分别怎样变化？
5. 结果在哪些条件下成立，还有什么未验证？
